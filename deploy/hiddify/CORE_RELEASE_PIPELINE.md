# Порядок выпуска двух Hiddify-ядер и использования их в 3x-ui

**Утверждённая последовательность: `hiddify-sing-box` → `hiddify-core` → `3x-ui`.**
Каждый следующий этап запускается только на **точно зафиксированном, проверенном SHA** предыдущего. Зелёный CI без необходимых функций не является критерием готовности.

## Этап 1. Довести hiddify-sing-box/main

1. Объединить рабочие изменения в `main` без повторного внесения уже перенесённого кода. Закрывать поглощённые PR без второго применения патча.
2. Исправлять ошибки **непосредственно в sing-box**, а не обходить тесты в `hiddify-core` или `3x-ui`.
3. Завершить все 16 функциональных групп 3x-ui overlay, включая 7 отсутствующих/частичных: `transport-balancer`, `vless-reverse`, `protection-options`, `sing-vmess-protection`, `sing-vmess-reverse`, `utls-protection`, `xray-runtime-compat`. Не считать частичный fail-closed эквивалентом полной реализации.
4. Обеспечить воспроизводимый граф зависимостей (при необходимости управляемые форки `sing-vmess`, `uTLS`, `Xray-core`) и регрессии Reverse, REALITY ML-DSA, Vision testseed, XHTTP, mKCP, UDP и наблюдения/балансировки.
5. Получить зелёные `Test`, `Lint`, `Upstream compatibility`, race/security и E2E для нужных платформ. **Записать конкретный `SINGBOX_SHA`.**

**Выходной артефакт:** один проверенный commit SHA `SawaMEN/hiddify-sing-box/main`. До этого шага **не обновлять** submodule/production pin `hiddify-core`.

**Состояние 2026-11-09:** PR [sing-box #23](https://github.com/SawaMEN/hiddify-sing-box/pull/23) слит в `main` коммитом `411bf2cc00ad332452a7ccd0d5ae973b733163a3`; пересекающийся PR [#22](https://github.com/SawaMEN/hiddify-sing-box/pull/22) закрыт как поглощённый. Резервная ветка `backup/pre-native-main-20261109` указывает на прежний `main` (`0dcb695697518f7999359ebbdcd0c8daf4d13e67`). После слияния дополнительно исправлены XHTTP lint и WARP RTT на Windows в коммитах `16065835`, `353d0324`. **Этап ещё не завершён:** 9/16 групп на уровне исходников, 7/16 отсутствуют или частичны, CI повторяется.

## Этап 2. Обновить hiddify-core и собрать проверенный бинарник

**Начинать только после всех условий этапа 1.**

1. Обновить `hiddify-sing-box` git submodule на **проверенный `SINGBOX_SHA`** и зафиксировать его в тестах/манифесте.
2. Обновить интерфейсы `hiddify-core`, парсер `ray2sing`, version/ABI, Go toolchain и security pins — без ослабления проверок.
3. Устранить наложение старых 3x-ui overlay в release builder: удалять/rebase только **подтверждённо перенесённые** группы, не пропускать недостающие опции ради зелёного CI.
4. Прогнать парсер, конфигурации 3x-ui, интеграционные тесты, Linux AMD64/ARM64 и Android ARM64; проверить запуск, `version`, `check`, TCP/UDP, перезапуск, обратную совместимость и угрозы.
5. Собрать релизные файлы `sing-box-linux-amd64.tar.gz`, `sing-box-linux-arm64.tar.gz`, их `.sha256`, сопроводительные `target.json`, `libcronet.so` и, где требуется, Android AAR/root companion.
6. Опубликовать **только полностью проверенный стабильный GitHub Release**: указать tag, `CORE_SHA`, `SINGBOX_SHA`, архитектуры, контрольные суммы.

**Выходной артефакт:** проверенный стабильный релиз `SawaMEN/hiddify-core` с Linux-бинарниками и манифестом. При неудаче — оставлять `hiddify-core/main` и production lock прежними.

**Состояние:** [core PR #20](https://github.com/SawaMEN/hiddify-core/pull/20) остаётся отдельной экспериментальной интеграцией; её release builder пока останавливается на `rebase-panel-protection.py` (6 конфликтующих файлов). Не публиковать её бинарник как стабильный.

## Этап 3. 3x-ui использует только готовое проверенное ядро

**Начинать только после стабильного релиза этапа 2.**

1. Для каждой сборки 3x-ui выбрать **самый новый полный стабильный GitHub Release** `hiddify-core` один раз и сохранить его тег во входах CI. Готовый бинарник внутри одного выпуска панели должен быть неизменным (для AMD64/ARM64). `target.json` хранит фактические `CORE_SHA` и `SINGBOX_SHA`; старый source-lock остаётся историческим контрактом.
2. Использовать существующий загрузчик `tools/fetch-latest-kernel.py --tag "$PIN" --arch amd64|arm64 --output ...`. Он проверяет SHA-256 архива и бинарника, архитектуру ELF, `target.json` и идентификатор версии. Дополнительно сверять SHA источника с lock.
3. В `.github/workflows/release.yml` всегда разрешать latest stable в отдельном job и скачивать уже выбранный тег из проверенного релиза. Не компилировать ядро в панели. На установленных Linux-серверах systemd timer проверяет новый релиз каждые 6 часов; перед заменой проверяет SHA-256, профиль, конфигурацию и делает резервную копию; при ошибке возвращает предыдущую версию.
4. Собрать **только саму панель 3x-ui**, затем упаковать вместе с ней проверенный бинарник ядра и Cronet. Проверить `core-migrate --check-binary`, контракт протоколов/опций и регрессии установки/обновления/отката.
5. При обновлении панели без изменения `CORE_SHA` / SHA-256 **переиспользовать прежний бинарник**. Существующий `scripts/migration/core-migration.sh` уже умеет безопасно сохранять побайтово идентичные core-артефакты.

**Итог:** компиляция ядра делается в CI `hiddify-core` **один раз для конкретной ревизии**. Сборка 3x-ui автоматически выбирает новый стабильный релиз; установленная панель проверяет обновление ядра независимо от новой версии самой панели. В случае ошибки/несовместимости старый рабочий бинарник остаётся на месте.

# OlcRTC в 3x-ui

OlcRTC работает отдельной службой. Его протокол и ссылки `olcrtc://` требуют
совместимого приложения; они не заменяют VLESS/VMess и не являются входящими
подключениями sing-box. Настройки остальных протоколов панель не меняет.

## Установка и клиенты

1. Откройте **Настройки → Системные пакеты и ядра Linux → Дополнительные
   компоненты → OlcRTC** и нажмите установку. Нужны root, systemd,
   Linux amd64/arm64, Debian/Ubuntu (apt) или Arch (pacman).
2. Дождитесь завершения. Панель проверяет авторизованный API службы,
   а не только выполнение `systemctl restart`.
3. Откройте **OlcRTC — клиенты → Настроить клиентов**. Идентификатор,
   ключ и случайная комната Jitsi генерируются при пустых полях.
   Для Телемоста и WB Stream создайте комнату у провайдера самостоятельно.
4. Скопируйте ссылку в совместимое приложение. Для Jitsi рекомендуется
   DataChannel, для Телемоста и WB Stream — VP8. Работоспособность комнаты
   зависит от доступности сервиса и сети VPS.
5. Обновление ставит только проверенную версию интеграции. Удаление
   сохраняет конфигурацию и ключи для повторной установки.

В Arch панель не выполняет частичное обновление `pacman -Sy` или полное
обновление ОС. Если системная база пакетов устарела, обновите ОС штатным
способом и повторите установку.

## Воспроизводимая сборка

Используются зафиксированные исходники:

- manager: `df626030d21d00286304bc8ef1e990e28c247a55`;
- сервер: `f3ad8fb7c0d0fa981423f83269526fa94077c23d`;
- исправления 3x-ui: `panel-v2`, файлы `internal/olcrtc/patches/`.

Патч проверяется через `git apply --check` и применяется до сборки.
Произвольные новые коммиты upstream не устанавливаются. Доступная версия
в панели означает проверенную комбинацию исходников и патча, а не последний
коммит внешних проектов. Обновление этой комбинации требует изменения кода,
проверки тестов и новой версии 3x-ui.

Go 1.26.3 скачивается в отдельную директорию
`/opt/3x-ui/olcrtc/toolchains/`. Архив проверяется по зафиксированной SHA-256
для amd64/arm64. Системные Go, `/usr/local/go` и симлинки не заменяются.
Отключены автоматическое переключение toolchain и наследование GOROOT,
GOFLAGS, локальных go env/work настроек. Пакеты и исходники скачиваются
по HTTPS; модульные зависимости остаются привязаны к upstream go.mod/go.sum.

Оба бинарника собираются в приватной временной директории до остановки
службы. При недостатке памяти используется последовательная сборка.
Автоматическое создание swap отключено. Неиспользуемая копия frontend
manager в `/opt/olcrtc-manager-src` не создаётся.

## Обновление и восстановление

Перед заменой файлов служба останавливается. Снимок включает оба бинарника,
systemd unit, конфигурацию, ключи, версию и прежнее active/enabled-состояние.
Журнал находится в `/etc/olcrtc-manager/.3x-ui-transaction/` с правами 0700.

Замена файлов выполняется через временные файлы и rename. После запуска
проверяется авторизованный `/api/settings`. При ошибке копирования, unit,
старта или проверки API снимок восстанавливается. Перед фиксацией успеха
данные синхронизируются с диском. При прерывании процесса или перезагрузке
незавершённый журнал восстанавливается при следующей попытке установки
или обновления, до новой сборки. Завершённый журнал не откатывается.

Не удаляйте журнал вручную при неудачном восстановлении: он содержит
предыдущую рабочую версию. Повторное обновление повторит восстановление.
При аппаратных ошибках диска или отказе systemd восстановление тоже может
завершиться ошибкой; снимок в этом случае сохраняется.

Во время обслуживания API клиентов отклоняет операции с понятной ошибкой,
чтобы создание/редактирование не пересекалось с заменой файлов. Таймаут
установки завершает всю группу процессов сборки, включая дочерние процессы.

## Исправления manager

- Изменения HTTP-конфигурации вместе с reload, reload по SIGHUP и фоновая
  запись квот используют одну общую блокировку read-modify-write.
- Запись выполняется через уникальный временный файл, fsync и rename.
  Несколько записей не используют общий `.tmp`.
- Ошибка применения конфигурации восстанавливает прежний файл и выполняет
  reload. Нельзя получить ошибку создания, оставив незаметно созданного
  клиента в конфигурации.
- При обновлении квоты текущие счётчики берутся из manager; переданными
  из браузера устаревшими значениями сбросить их нельзя.
- Сетевые счётчики учитывают RX и TX. Их база обновляется только после
  успешного сохранения; неудачная запись не теряет накопленный интервал.
  Перед штатной остановкой выполняется последняя запись до остановки туннелей.
- Ошибки `ip_forward`, правил NAT/FORWARD и обязательного ограничения
  скорости возвращаются вызывающему коду. Неудачно настроенный процесс
  останавливается; ложного успеха установки ограничителя нет.
- После неудачного создания namespace удаляются созданные veth, namespace,
  resolv.conf и правила, принадлежащие этому namespace.

Квоты измеряют сетевой трафик namespace, включая накладные расходы
транспорта; это не счётчик только полезных данных приложения. Проверка
лимита выполняется периодически, поэтому возможен трафик между проверками.

## Безопасность и диагностика

Менеджер слушает только `127.0.0.1`. Его TLS отключён на уровне systemd,
в том числе при сохранённых TLS-настройках в `panel.env`. Пароль остаётся
на сервере; панель обращается через локальную Basic-аутентификацию.
Локальный HTTP-клиент не использует прокси окружения и перенаправления.
API 3x-ui наследует сессию администратора/admin-token и CSRF-защиту.

Сбой `hostname -I` устранён: внешний IP не определяется для локальной
HTTP-службы. Ошибки установки показывают безопасное имя этапа. Полный лог
последней неудачной установки — `/var/log/3x-ui/olcrtc/install.log` (0600,
директория 0700). Он может содержать секреты: не публикуйте его целиком.

Для локальной диагностики от root:

```bash
systemctl status olcrtc-manager
journalctl -u olcrtc-manager -n 100 --no-pager
less /var/log/3x-ui/olcrtc/install.log
```

Успешная установка и запущенный процесс не подтверждают соединение с
провайдером: отдельно проверьте реальным клиентом комнату, передачу данных
и доступность сервиса из сети VPS. Сбой live-метрик больше не препятствует
загрузке списка клиентов; копирование ссылки использует общий механизм
панели с поддержкой HTTP-интерфейса.

## Проверки

Регрессионные тесты проверяют раннюю инициализацию установщика, ошибку
второй сборки, успешное развёртывание, откат после ошибки копирования и
проверки API, восстановление после SIGKILL, сохранность файлов, секретов
и запрет операций клиентов во время обслуживания.

CI применяет патч к зафиксированному manager и запускает его исходные
тесты и новые тесты с `-race`. На отдельной Ubuntu VM проверяются настоящие
namespace, veth, передача TCP, сетевые счётчики, настройка `tc` и очистка,
затем production-установка и авторизованный API под systemd. Arch проверяет
пакетный путь и фактическую инициализацию установщика.

API: `/panel/api/olcrtc/status|live|clients`, POST
`install|update|remove|restart`; клиенты — POST `clients`, PUT
`clients/:id` (или POST `clients/:id/update`), POST
`clients/:id/delete|rotate-key`. Пользовательские поля:
`client_id`, `carrier`, `transport`, `room_id`, `key`, `dns`, `name`,
`quota.speed_mbps`, `quota.traffic_gb`, `quota.expires_at`.

# OlcRTC — отдельный WebRTC-сервер в 3x-ui

## Что интегрировано

Окно **Настройки → Системные пакеты и ядра Linux → Дополнительные компоненты → OlcRTC**
служит только для установки, обновления и удаления бинарников OlcRTC.
Управление пользователями и перезапуск службы вынесены в самостоятельный
пункт бокового меню **OlcRTC — клиенты** (адрес `/panel/olcrtc`).
До подтверждения установки сервером этот пункт в боковом меню скрыт.
Старые закладки `/panel/settings#olcrtc` автоматически перенаправляются сюда.
Входящие подключения sing-box при этом не изменяются.

OlcRTC использует [openlibrecommunity/olcrtc](https://github.com/openlibrecommunity/olcrtc)
(собственно WebRTC-туннель) и
[BigDaddy3334/olcrtc-manager-panel](https://github.com/BigDaddy3334/olcrtc-manager-panel)
(процессы клиентов, квоты и конфигурация). Исследованный
[owenewans/snolc](https://github.com/owenewans/snolc) — **другой**
Rust-движок с собственными модулями и форматом `wire_version=1`; это не тот
же протокол, его бинарники нельзя использовать вместо `olcrtc`.

## Установка и управление

1. Откройте окно обновлений Linux, найдите OlcRTC и нажмите установку.
2. Операция выполняется сервером асинхронно; карточка показывает ход работы
   и ошибки. Поддерживаются **Debian/Ubuntu (apt)** и **Arch Linux (pacman)**,
   Linux amd64/arm64 под systemd. В Arch используются пакеты из системной базы
   pacman без принудительного `pacman -Sy` или полного обновления ОС.
   При устаревшей базе пакетов обновите систему штатно с `sudo pacman -Syu`
   самостоятельно и повторите установку.
3. После успешного запуска откройте отдельную страницу **OlcRTC — клиенты** и используйте **Настроить клиентов**. Если служба
   остановлена, доступна кнопка **Перезапустить службу**.
4. Создайте клиента: идентификатор, ключ шифрования и URL комнаты Jitsi
   сгенерируются автоматически, если оставить их пустыми. Скопируйте ссылку
   `olcrtc://` в приложение, **умеющее работать с OlcRTC**.
5. В списке клиентов выводится краткая диагностика: запущен ли туннель и сколько
   участников сейчас подключено. Данные загружаются по кнопке «Обновить».
6. Для Яндекс Телемоста и WB Stream сначала создайте комнату у провайдера
   и введите её ID. Транспорт выбирайте среди показанных совместимых.
7. Кнопка обновления пересобирает текущие upstream-источники и перезапускает
   службу. Кнопка удаления останавливает и отключает службу, удаляет
   установленные бинарники и systemd unit.

Клиентские настройки и секреты `/etc/olcrtc-manager/config.json` и
`/etc/olcrtc-manager/panel.env` **сохраняются при удалении** для
возможной переустановки. Это не резервная копия; перед переходом на новый
upstream рекомендуется отдельно сохранить директорию.

## Важные детали

- Служба `olcrtc-manager.service`, бинарники `/usr/local/bin/olcrtc` и
  `/usr/local/bin/olcrtc-manager`. Доступ к административному API
  менеджера ограничен `127.0.0.1`; запросы клиентов проходят через
  защищённый API 3x-ui и локальную Basic-аутентификацию менеджера.
- Установка использует зафиксированную версию upstream **скрипта
  установщика**; на Arch к нему добавляется ветка `pacman` для установки зависимостей. Скрипт собирает последние ветки `main` менеджера и
  `master` сервера. Внешний код исполняется от root после явного нажатия
  кнопки. В файл версии записываются фактические SHA двух checkout, а не состояние
  удалённых веток после сборки. Для воспроизводимости между установками
  по-прежнему требуется зафиксировать исходные ревизии компонентов.
- Доступная версия отображается как git-ревизии двух upstream-веток, в том
  числе до установки. Если git отсутствует или GitHub недоступен, вместо
  фиктивного значения «upstream» показывается «—». Начальная установка
  при этом остаётся доступной.
- Код ошибки 127 означает, что установщик не нашёл исполняемую команду.
  Панель показывает безопасную диагностику без передачи лога (он может
  содержать учётные данные). Для процесса установки задаётся системный
  PATH с `/usr/local/bin` и `/usr/local/go/bin`.
- На локальной установке не вызывается `hostname -I`: GNU inetutils (Arch)
  не поддерживает эту опцию, что раньше обрывало глобальную инициализацию
  установщика с кодом 64 ещё до установки пакетов.
- Оба бинарника сначала собираются в приватной временной директории.
  Ошибка второй сборки больше не заменяет первый установленный бинарник.
  Временные исходники удаляются при завершении; копия upstream-панели
  в `/opt/olcrtc-manager-src` больше не создаётся.
- После перезапуска проверяется авторизованный `/api/settings` на loopback
  в течение 30 секунд. Самого `systemctl restart` недостаточно для успеха.
  Флаг `-addr 127.0.0.1` и `UnsetEnvironment` для TLS гарантируют HTTP на
  loopback даже при сохранённых TLS/bind-параметрах в `panel.env`.
- При ошибке сборки/установки API показывает только разрешённое имя этапа.
  Полный лог сохраняется в `/var/log/3x-ui/olcrtc/install.log` с правами 0600
  внутри директории 0700. Лог может содержать пароли: читать только локально
  от root, не публиковать и не прикладывать целиком к обращениям.
- Исходный менеджер создаёт отдельные network namespaces, veth, NAT и
  ограничители скорости `tc` для клиентов. Нужны `ip`, `iptables`,
  `tc` и достаточно памяти для сборки Go.
- Новый клиент Jitsi создаёт случайный URL комнаты на
  `https://meet.handyweb.org`. Его работоспособность зависит от текущей
  доступности Jitsi-провайдера и настроек самого сервиса.
- Для Яндекс Телемоста предпочтителен `vp8channel`, для Jitsi —
  `datachannel`, для WB Stream — `vp8channel`. Не все сочетания работают.
  Утверждений о гарантированном обходе фильтрации не делается.
- Это **не новая нативная реализация OlcRTC внутри sing-box**: она работает
  как независимый WebRTC-туннель. Формат `olcrtc://` не является
  автоматически совместимым с Xray/VLESS/VMess или клиентами sing-box.

## Ручная диагностика

```bash
systemctl status olcrtc-manager
journalctl -u olcrtc-manager -n 100 --no-pager
cat /etc/olcrtc-manager/config.json
```

Конфигурация может содержать секретные ключи; не публикуйте вывод третьей
команды.

API панели (требуется сессия администратора / admin API token):

- `GET /panel/api/olcrtc/status`
- `GET /panel/api/olcrtc/live` — суммарные активные процессы и участники,
  краткое состояние клиентов без секретных ключей, ID комнат и параметров прокси
- `POST /panel/api/olcrtc/install|update|remove|restart`
- `GET /panel/api/olcrtc/clients`
- `POST /panel/api/olcrtc/clients`
- `PUT /panel/api/olcrtc/clients/:id`
- `POST /panel/api/olcrtc/clients/:id/delete`
- `POST /panel/api/olcrtc/clients/:id/rotate-key`

Для создания/обновления используются JSON-поля `client_id`, `carrier`,
`transport`, `room_id`, `key`, `dns`, `name`, необязательный объект
`quota` (`speed_mbps`, `traffic_gb`, `expires_at`).

## Результаты аудита интеграции

Проверены установщик manager `df626030d21d00286304bc8ef1e990e28c247a55`,
обёртка Go, systemd unit, CRUD/rotate-key API, формат ссылок, отображение
клиентов и статуса в React, зависимости и существующий CI.

Исправлены: аварийный ранний `hostname -I`, отсутствие этапа ошибки,
потеря полного диагностического лога, общие имена временных бинарников,
частичное обновление при ошибке второй сборки, утечка временной директории
из-за EXIT trap с уже вышедшей из области видимости local-переменной,
неверная фиксация собранной версии, сохранённый TLS вместо локального HTTP,
отсутствие проверки готовности API. Локальный HTTP-клиент не использует
прокси окружения и не следует перенаправлениям с административной авторизацией.

Ограничения, которые остаются:

- Это интеграция двух внешних программ. Их исходники берутся из движущихся
  upstream-веток, поэтому успешная установка сегодня не гарантирует
  совместимость будущих изменений API или Go-зависимостей. Нужен отдельный
  процесс обновления проверенных, зафиксированных ревизий.
- Сборка выполняется на VPS; upstream `install_go` может менять глобальную
  `/usr/local/go`. Следующий архитектурный шаг: проверенные готовые артефакты
  либо отдельный toolchain компонента. Автоматическое создание swap отключено.
- Сборочные ошибки сохраняют старые бинарники; замена двух файлов, unit и
  перезапуск пока не являются транзакцией с полным откатом при сбое диска
  или ошибке запуска. Маркер принадлежности записывается до запуска службы,
  чтобы запуск можно было повторить через Update/Remove.
- Внешний manager использует read-modify-write конфигурации и общий файл
  `.tmp` без общей блокировки всех HTTP-изменений и фонового учёта квот.
  Одновременные операции могут конфликтовать; это требует исправления
  manager, одной блокировки в 3x-ui недостаточно.
- Ошибки настройки `ip_forward`, NAT и части ограничителей в upstream
  местами логируются без отказа запуска. Процесс running не подтверждает
  доступность туннеля, корректность учёта трафика или соблюдение скорости.
  Для гарантий нужны отдельные сетевые испытания с реальными клиентами.
- Локальные unit/регрессионные тесты проверяют интеграцию, а не доступность
  Jitsi/Телемост/WB Stream из сети конкретного VPS. Установка в настоящем
  systemd и авторизованный API проверяются отдельным CI smoke-тестом,
  который вызывает production-функцию `install`, а не исходный скрипт напрямую.

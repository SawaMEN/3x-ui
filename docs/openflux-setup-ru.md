# OpenFlux в 3x-ui: настройка и диагностика

Инструкция для панели **3x-ui** и OpenFlux 0.17.1 (последний стабильный выпуск, проверен 18.11.2026).

## Быстрый старт

1. Откройте **Настройки → Установка и обновление компонентов** и проверьте установку OpenFlux на **той же ноде**, где будет inbound.
2. Создайте inbound типа OpenFlux (один inbound поддерживает одну активную сессию). Секрет и контекст шифрования генерируются при сохранении; не изменяйте их по отдельности.
3. Добавьте канал, следуя инструкции внутри его карточки, сохраните inbound и включите его.
4. Откройте ссылку подключения `openflux://` в совместимом клиенте либо импортируйте её в редактор исходящего OpenFlux. MAX использует отдельную клиентскую конфигурацию, а не общий QR.
5. Проверьте реальный трафик **с другого устройства** через клиент (для CLI — SOCKS5 `127.0.0.1:1080`). Только этот шаг подтверждает рабочий туннель.

## Yandex Docs (Volga, `vyandex`)

Нужен **текстовый документ DOCX**, НЕ таблица XLSX и не презентация.

1. Перейдите на https://docs.yandex.ru/ и войдите в свой аккаунт.
2. Создайте **новый текстовый документ**. В самом редакторе включите опцию **«Перейти на новый редактор»**, если доступна. Для нового редактора выберите транспорт **Yandex Docs (Volga)**; для старого (классического) — **Yandex Docs (WebSocket)**.
3. Нажмите **«Поделиться»**, включите доступ по ссылке с правом **редактирования**.
4. Копируйте **ссылку общего доступа** (например, `https://disk.yandex.ru/i/...`), а не случайный URL страницы просмотра/списка файлов.
5. Вставьте полную HTTPS-ссылку в поле канала. У сервера и клиента должна быть **одна и та же ссылка**. Не меняйте тип редактора без изменения транспорта.
6. Если появляется капча или запрос авторизации, откройте документ в официальном клиенте/браузере. Для Volga возможно использование сессионных cookies; сам факт открытия ссылки не подтверждает передачу OpenFlux-пакетов.

Используйте отдельный документ для каждого независимого inbound; считайте публичную ссылку чувствительным идентификатором канала.

## MAX / OneMe (`oneme`)

**Это не MAX Bot API.** Транспорт OpenFlux использует **токен сессии веб-пользователя MAX**, а не ключ чат-бота на https://dev.max.ru/. Нужны **два разных пользовательских аккаунта**: серверный и клиентский.

1. Авторизуйтесь в **своём серверном аккаунте** по адресу https://web.max.ru/ в настольном браузере.
2. Откройте средства разработчика (F12), вкладку **Network/Сеть → WS/WebSocket**. В соединении `wss://ws-api.oneme.ru/websocket` после обычного входа можно исследовать собственные исходящие кадры: у авторизационного сообщения с **opcode 19** полезная нагрузка содержит `payload.token`. Это секрет, который требуется OpenFlux для `maxToken` / `oneme-token`. Не путайте его с токеном бота и не публикуйте скриншоты или журнал с токеном.
3. В поле **«Токен Web MAX сервера»** укажите этот токен. В поле **«ID аккаунта MAX сервера»** нужен числовой **ID пользователя**, а не номер телефона. Его необходимо сверить по данным своего профиля/веб-сессии: без корректного серверного ID создание клиентской конфигурации невозможно.
4. Войдите во **второй аккаунт** MAX на клиентском устройстве и получите **его отдельный токен веб-сессии** аналогичным образом.
5. В 3x-ui откройте настройку **«Подключить клиент через MAX»**, укажите токен второго аккаунта и скачайте ZIP с конфигурацией и общим секретом. **Токен сервера в архив не включается.**
6. Запустите CLI OpenFlux из архива или вручную перенесите секрет, контекст, **клиентский токен** и **ID сервера** в совместимый клиент.

Метод основан на текущем веб-протоколе MAX, **не является официальной выдачей токенов разработчикам** и может перестать работать при изменении веб-клиента. Никогда не вводите свои токены в посторонние сервисы.

### Остальные каналы

| Канал | Что использовать |

| Direct | Публичный IP/домен и открытый TCP-порт сервера |
| Yandex Docs (WebSocket) | Текстовый DOCX в старом редакторе и его общую ссылку |
| Yandex Boards | Общую ссылку на отдельную доску |

| Yandex Telemost | Ссылку на действующую конференцию |

## Что означает «Проверить доступность сервиса»

Кнопка в карточке выполняет запрос к **собственной панели**. Сервер проверяет только DNS, TCP и TLS к заранее заданному публичному адресу сервиса. Произвольные URL, токены, контексты и ключи **не отправляются**. Попытки проверить произвольный адрес отклоняются, чтобы диагностика не стала SSRF-прокси.

* **Успех** — провайдер доступен с этой машины по TLS на порту 443; это **не** означает, что канал OpenFlux уже работает.
* **Ошибка** — проблема установки компонента или сетевой доступности провайдера с этой машины; проверьте DNS/файрвол/исходящий трафик.
* **Direct** — проверяйте с другого устройства, а не с сервера.
* **Удалённые ноды** — тест с управляющей панели намеренно недоступен: он измерял бы не ту машину.

Для полноценной диагностики необходимы **включённый inbound, клиент с тем же ключом и контекстом, успешная сессия и реальная передача данных**. На текущий момент кнопка не выполняет этот e2e-тест.

## Известные ограничения и проверки

* Для каждого inbound поддерживается одна активная сессия; отдельному устройству/пользователю лучше выделять отдельный inbound.
* Загрузка, проверка SHA-256, запуск `--help`, конфигурация и шифрованный TCP-тест покрыты автоматическими тестами. Эти тесты не проверяют живые аккаунты MAX или права на пользовательские документы.
* В исходном коде OpenFlux `transport/oneme/max_transport.go` метод `Start()` на момент ревизии этой инструкции не обрабатывает ошибки `Connect()` и `LoginByToken()`, а `IsConnected()` возвращает `true`. Поэтому **считать MAX рабочим только по старту процесса нельзя**. Требуется реальный клиентский вызов/обмен трафиком; исправление поведения находится в upstream OpenFlux.
* Сохранение и работа с MAX-токенами подразумевает отдельные личные аккаунты. При ошибке токена не пытайтесь использовать токен чат-бота как замену.

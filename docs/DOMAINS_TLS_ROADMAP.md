# Домены и TLS — карта развития (ветка domen)

## Цель и границы

Панель 3x-ui сохраняет существующие Go-сервисы, шлюз и CertMagic, SNI на нодах, Telemt WEB и конфигурации подписок. Nginx Proxy Manager (NPM) используется **как эталон интерфейса и сценариев**, но его Node.js/nginx/Certbot-стек не копируется и не вводится как обязательная зависимость.

## Этап 2 — диагностика готовности (реализовано)

- `POST /panel/api/domains/preflight` анализирует **несохранённую** конфигурацию и возвращает `ready`, `checkedAt`, `checks` (severity, code, domain, message, addresses); не создаёт сертификатов и не изменяет настройки.
- Для `shared_sni` не проверяются локальные сертификаты и не выделяются локальные порты; файлы остаются на соответствующей ноде.
- Проверки DNS работают с пределом 6 секунд и не более четырьмя рабочими запросами; нет TCP-соединения к DNS-результатам, что исключает SSRF через этот маршрут.
- Проверки портов только кратковременно пытаются открыть и закрыть сокет. Если порт занят действующим шлюзом, это отмечается отдельно. Занятость произвольного порта — **предупреждение**, поскольку у панели и подписок может быть совместное использование listener.
- Ошибки валидации, конфликт локального шлюза с Telemt WEB и ошибки ручного сертификата блокируют применение в интерфейсе. DNS и спорные порты — только предупреждения; администратор подтверждает продолжение.
- При нажатии «Сохранить и применить» выполняется новая предварительная проверка, без повторного использования устаревшего статуса.
- Backend тесты: `internal/web/service/domain_preflight_test.go`, `internal/web/controller/domains_preflight_test.go`; UI тесты в `frontend/src/test/domain-front-tab.test.tsx`.

**Ограничения:** preflight не заменяет атомарную проверку во время `apply`; состояние DNS/портов может измениться после диагностики. Невозможно доказать доступность публичного HTTP-01 без внешнего проверяющего узла. Программная проверка не должна изменять ACME, DNS или права ноды.

## Этап 3 — сертификаты разных менеджеров и временный файрволл

- Единый реестр объединяет локальные сертификаты CertMagic, acme.sh, Certbot, ручные файлы и удалённые SNI без передачи приватных ключей. Метаданные включают SAN, issuer, срок, владельца и способ проверки.
- Отдельный `POST /panel/api/domains/certificates/renew` принимает только ID локального известного сертификата, определяет менеджер по уже существующему источнику и выполняет штатную команду **без shell**. Ручное продление CertMagic не подменяется командой Certbot.
- Фоновый планировщик каждые 12 часов проверяет **локальные** сертификаты acme.sh/Certbot, срок которых заканчивается не позже 30 дней, с лимитом попыток раз в 24 часа. Решение об актуальной необходимости продления принимает сам acme.sh или Certbot. Команды ограничены 12 минутами, операции по внешним сертификатам сериализованы.
- Временная аренда файрволла использует поддерживаемый штатным 3x-ui backend UFW/firewalld/nftables/iptables; TCP 80 для HTTP-01, TCP 443 для TLS-ALPN-01, **ни одного входящего порта для DNS-01**. Аренда записывается до начала проверки и удаляется по её завершении с повторной синхронизацией. Существующие правила администратора не удаляются, порты постоянно работающего веб-шлюза остаются открыты.
- Для CertMagic подключены события `cert_obtaining`, `cert_obtained`, `cert_renewed`, `cert_failed`; heartbeat продлевает временное правило во время долгой операции, после завершения правило снимается. Для локального acme.sh/Certbot штатные команды запускаются под scoped-wrapper с восстановлением даже при ошибках.
- Для **независимых cron/systemd продлений** добавлен root-only Unix-сокет `certificate-renewal.sock` с правами `0600` и CLI `x-ui certificate-hook begin|end certbot|acme.sh [parent-pid]`. CLI **не открывает файрволл сам**, а запрашивает аренду у уже работающего процесса панели. Менеджер и необходимые порты вычисляются на сервере по локальному реестру, произвольные пути/порты от внешнего процесса не принимаются.
- Хуки Certbot автоматически размещаются в `/etc/letsencrypt/renewal-hooks/{pre,post}/3x-ui-certificate-firewall`, когда у панели действительно есть сертификаты Certbot. Для известных локальных сертификатов acme.sh в конфиге заполняются **только пустые** `Le_PreHook` / `Le_PostHook`; существующие пользовательские хуки сохраняются, конфликт отмечается в логе. Сгенерированные скрипты используют абсолютный путь к запущенному бинарному файлу.
- Внешний pre/post-hook открывает порт перед проверкой и закрывает после её окончания. Если post-hook пропущен из-за сбоя, панель отслеживает PID родительского процесса и закрывает его аренду после выхода; при рестарте панели другие process-ID теряют право удерживать аренду, а плановый reconcile очищает устаревшие правила. Независимые параллельные аренды не закрывают порты друг друга.
- **Граница гарантии**: Certbot, запущенный с `--no-directory-hooks`, и acme.sh с установленными администратором пользовательскими хуками не могут быть автоматически перехвачены без изменения чужих сценариев. В этих случаях использовать встроенный планировщик 3x-ui, либо вручную интегрировать предоставленный CLI в собственные pre/post-hooks. Облачный файрволл хостера и сетевой NAT панель не изменяет; TCP 80/443 должны реально вести к правильному HTTP/TLS обработчику.
- Не выполнять автоматическое продление для сертификатов неизвестного менеджера, ручных сертификатов и чужих нод. Не изменять DNS-токены, не затирать существующие хуки сторонних утилит и не публиковать вывод программ, если он содержит секреты.

## Дальнейшие задачи (не реализованы)

1. **Проверка готовности** перед применением: реализованы синтаксическая и сертификатная валидация, конфликты Telemt на TCP 443, read-only проверки портов, ограниченные по времени DNS-запросы, проверка ручных сертификатов и явное подтверждение предупреждений. **Не реализовано**: доказательство доступности HTTP-01 извне и подтверждение соответствия DNS IP конкретной ноды; результаты этих аспектов имеют информационный/предупредительный статус.
2. **Управление сертификатами**: реестр, issuer/SAN и ручное продление для локальных acme.sh/Certbot реализованы; ещё нужен подробный журнал попыток всех менеджеров и безопасное управление CertMagic.
3. **DNS-01**: провайдеры DNS через ограниченные токены, безопасное хранение и маскирование секретов, wildcard, поддержка propagation и rate limits; не переносить Python-плагины Certbot напрямую.
4. **Мульти-ноды**: проверка адресов и сертификатов с точки зрения каждой ноды; отдельные нодовые права и контроль размещения файлов сертификатов.
5. **Мониторинг**: фоновый опрос со стороны сервера с лимитами, события об истечении/ошибке, уведомления администратора и история действий.

## Защита от неожиданных изменений

- Только `/panel/api/domains/apply` применяет конфигурацию; проверка `/panel/api/domains/check` остаётся read-only и использует существующую защиту от SSRF.
- Клиент не читает приватные ключи: отображаются только пути сертификатов, уже доступные администратору.
- Файлы сертификатов удалённых нод не используются на основной ноде.
- Проверки публичного TLS могут не сработать для недоступных из панели доменов; такая ошибка не должна автоматически удалять домен или сертификат.
- Изменения делаются в `domen`; `main` не меняется без отдельного решения.

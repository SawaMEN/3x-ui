## Исправления

Экспорт PostgreSQL больше не удаляет существующий файл перед проверкой
соединения и копированием. Новая копия строится в соседнем временном файле,
закрывается и только после успеха заменяет назначение через rename. Ошибка
не уничтожает предыдущую копию. Файл создаётся с правами 0600.

Перенос читает все таблицы из одного снимка: SQLite read transaction или
PostgreSQL REPEATABLE READ. Схема и строки назначения создаются в одной
транзакции. Sequences при импорте меняются через транзакционный
`ALTER SEQUENCE RESTART`, вместо неоткатываемого `setval` после commit.
Строковые ID, включая квитанции TUIC, исключены из числового resync;
ошибки больше не игнорируются.

Копирование читает значения столбцов напрямую, сохраняя SQL NULL, false,
JSON и поля credentials, скрытые от API. Прежний путь через Go-модели мог
превращать NULL в нулевые значения и повторно сериализовать JSON.

SQL-дамп получает общий снимок схемы/данных/индексов, сохраняет BLOB как BLOB,
пустые двоичные значения и TEXT с нулевыми байтами. Имена таблиц экранируются.
Неполный дамп без COMMIT, дамп без таблиц и повреждённые SQLite-файлы больше
не подтверждаются как успешно восстановленные. Ограничение ATTACH/VACUUM INTO
сохранено. Backup/restore резервируют назначение через O_EXCL с правами 0600;
SQL-дамп заменяет старый файл атомарно и ужесточает прежние права.

## Оптимизация и удаление лишнего

- Убрано промежуточное создание отражённых Go-объектов и повторных карт полей
  при переносе каждой строки; исходные значения используются непосредственно.
- Растущий OFFSET заменён keyset pagination по простому/составному PK;
  fallback OFFSET остаётся для таблиц без PK. Размер INSERT зависит от числа
  столбцов, с бюджетом 999 параметров для SQLite и 65 535 для PostgreSQL.
- Буферы SQL-сканирования дампа создаются один раз на таблицу, не на строку.
- `bytes.Buffer.Bytes()` убирает дополнительную полную копию дампа.
- Удалено избыточное создание каталога источника после успешного Stat файла.

Бенчмарк на 10 000 строк, по три прогона: память примерно **3 573 976 →
3 254 059 B/op (−9%)**, аллокации **59 692 → 49 695 (−17%)**. Время
заметно колеблется; устойчивое ускорение по этим замерам не заявляется.

## Воспроизведения и границы

На настоящем worktree `v3.9.8` тест заполненных sessions/routing presets
воспроизводит `UNIQUE constraint failed: routing_presets.id` из-за повторов
в списке моделей. В целевом main этот старый дефект уже был исправлен;
его нельзя считать новым исправлением этапа 3.

На предшествующем `f1e42abe` новые регрессии воспроизводят принятие дампа
без COMMIT, потерю прежнего export-файла и неверное экранирование имени таблицы.
После изменений локальные регрессии проходят. Верификация сравнивает поля
данных, включая ключи, хеши сессий, лимиты и счётчики, а не только число строк.

Fixture синтетическая: исходные 22 inbound-профиля/21 protocol ID, 51 клиент,
связи/трафик, hosts/groups, HWID, node, session/preset и сертификаты. Для
переноса дополнительно заполняется каждая из 30 текущих таблиц. Это проверка
хранения, а не сетевых handshake всех протоколов.

Согласованность SQL-дампа и native backup проверяется при параллельном
обновлении связанных таблиц и payload 4 MiB в WAL. Это не испытание максимального
размера производственной БД. Инъекция full использует настоящий SQLite pager с ограничением max_page_count;
она не заполняет файловую систему хоста. Это не испытание физического отказа
диска или потери питания. Перезапись работающей SQLite-БД экспортом не является
поддерживаемой процедурой: восстановление выполняется при остановленной панели.
Откат версии — восстановлением совместимого snapshot; старый бинарник не
запускается на новой схеме.

Первые неудачные прогоны сохранены: serializer в тестовом сравнении, ранее
игнорируемая ошибка sequence для text ID, отсутствие client-16 на движущемся
ubuntu-latest и опечатка вспомогательного пути в промежуточном коммите.
Эти прогоны не зачтены как успешные; runner закреплён на Ubuntu 24.04.

Дополнительно убран `TRUNCATE … CASCADE`: миграция отказывается от очистки,
если внешняя таблица ссылается на данные панели. Проверяется сохранение
внешней строки и всех прежних записей панели после такого отказа.

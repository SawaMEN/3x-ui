# Диагностика каскадной маршрутизации между нодами

Страница `/panel/cascade-diagnostics` открывается через меню **Диагностика каскадов**.
Все подписи в интерфейсе на русском. Панель не является отдельным публичным
сайтом: она работает внутри авторизованного 3x-ui, используя те же права
доступа, CSRF и базовый путь развернутой панели.

## Схема

`Клиент → локальное inbound → правило маршрутизации → node-route-ID →
служебный outbound → удалённое inbound ноды → удалённый egress → интернет`

`node-route-ID` — управляемый тег исходящего. Его настройки и сервисные
секреты генерируются сервером на лету; пароли и ссылки подключений не выводятся
на эту страницу и не попадают в локальный отчёт.

## Порядок диагностики

1. Выберите ядро источника (Xray или sing-box), удалённую ноду, её входящее и
   входящее-источник, откуда должен приходить клиентский трафик (в том числе на иной ноде).
2. Убедитесь, что удалённое inbound включено и протокол совместим с ядром источника.
3. Нажмите **Проверить каскад**. Метод
   `POST /panel/api/xray/node-route/probe` сначала проверяет настроенный
   служебный outbound; когда он поддерживает аутентифицированный HTTP-тест,
   факт успешного HTTP отражается отдельно от проверки TCP/UDP.
4. Для Xray дополнительно проверяется ожидаемый тег через
   `POST /panel/api/xray/routeTest` (синтетический запрос). Для sing-box API
   проверки выбора маршрута недоступен; это отображается как непроверенный
   этап, а не как успешная маршрутизация.
5. Если нужно переустановить служебное соединение, нажмите **Подготовить**:
   после подтверждения вызывается `POST /panel/api/xray/node-route/ensure`.
   Операция может создать/обновить служебного клиента и перезапустить ядро
   удалённой ноды, что может оборвать текущие соединения.
6. После применения изменений **повторно выполните** проверки. Отдельно
   проверьте реального клиента через исходное inbound и сопоставьте
   свежие серверные логи обеих нод с ожидаемой схемой маршрута.
7. Вручную зарегистрируйте обнаруженные проблемы, меняйте их статус:
   «Открыта» → «Исправлена» → «На повторную проверку» → «Проверена».
   К каждому исправлению приложите результат теста или ссылку на лог.

### Ограничения достоверности

- Простой TCP/UDP dial **не доказывает** авторизацию или передачу данных.
- Успешный HTTP-тест служебного outbound выполняется с сервера панели.
  Он **не подтверждает** реальный маршрут пользовательского inbound.
- Синтетический routeTest определяет выбранный исходящий **локального** Xray, но сам по себе
  не передаёт трафик. Для источника на удалённой ноде проверка маршрута
  помечается неисполненной: локальный API не наблюдает её ядро.
- При недоступности API или отсутствии поддерживаемого теста этап остаётся
  не проверенным. Он не становится успешным по умолчанию.
- Журнал операторских проблем, чек-лист, история проверок и состояние подготовки
  хранятся в `localStorage` текущего браузера, а не в базе данных кластера.
  Для передачи результатов используйте **Экспорт отчёта JSON**.
  Не записывайте в ручные поля пароли, ключи или персональные данные.

## Подготовка к main

1. Проверить изменения через `npm run typecheck`, `npm test` и
   необходимые GitHub Actions.
2. Подготовить трассировки или результаты сквозного клиентского теста для
   каждого задействованного каскада с датой, тегами и типом протокола.
3. Устранить все ошибки; убедиться, что повторные проверки не возвращают
   маршрут в состояние ошибки.
4. Заполнить чек-лист и приложить ссылки на доказательства; CI и ревью
   подтверждаются вручную, панель не подменяет статус GitHub.
5. Только после этого переводить PR из draft в review и сливать в `main`.
   Интерфейс не выполняет merge автоматически и не обходит проверок.

## Матрица проверок

| Этап | Источник | Что означает зелёный статус |
| --- | --- | --- |
| Нода и inbound | `node-route/targets` | Метаданные доступны для подготовки |
| Сетевой порт | `node-route/probe` | Порт или проверенный туннель доступен |
| Авторизация и HTTP | `node-route/probe` | `tunnelChecked && reachable` |
| Выбор маршрута Xray | `xray/routeTest` | Точный `outboundTag = node-route-ID` |
| Реальный пользовательский поток | Отдельные логи и клиентский тест | **Никогда автоматически не считается пройденным** |

При отсутствии доказательств полного каскада не следует сообщать, что
исправления завершены и проверены. Для разных протоколов и для sing-box
дополнительная реализация сквозного тестирования может потребоваться отдельно.

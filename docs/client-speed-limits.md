# Ограничение скорости клиента

В форме создания или редактирования клиента включите «Ограничение скорости трафика» и укажите загрузку и отдачу в Мбит/с. По умолчанию функция выключена. Ноль оставляет соответствующее направление без ограничения; при включении хотя бы одно значение должно быть положительным. Допустимые значения — целые числа от 0 до 100000.

Лимит действует на сервере, не требует изменения клиентского приложения и делится между TCP- и UDP-соединениями одной клиентской записи, включая подключения через разные входящие. Другие клиенты используют собственные лимиты или работают без ограничения. Начальный кратковременный всплеск допускается в пределах 64 КиБ на направление. Внутренняя обработка DNS ядром сохраняется отдельно от ограничения проксируемых соединений.

Поддерживаются VMess, VLESS, HTTP, Mixed, Trojan, Shadowsocks, Hysteria2, TUIC, NaiveProxy, AnyTLS, Snell, ShadowTLS, Mieru, Sudoku и MASQUE. Для WireGuard, AmneziaWG, MTProto и остальных внешних протокольных служб включённый лимит отклоняется: им нужен отдельный механизм идентификации/ограничения, а не фиктивное поле в панели. При ограничениях Hysteria2 используется встроенное ядро, сохраняющее идентификацию пользователя.

Ограничение общее для соединений клиента на **одном сервере**. На удалённых нодах нужно установить эту же версию панели; каждая нода применяет свой лимит независимо. Это не распределённая квота скорости на весь кластер. Внешние ссылки в подписке также не управляются этим сервером.

При изменении плана ограничений текущие соединения ограничиваемых клиентов закрываются и переподключаются. Маршрутизация, блокирующие правила и выбор исходящего подключения сохраняются; повторный проход через ядро не учитывается как дополнительный клиентский трафик.

Только для ограничиваемых клиентов добавляется локальный SOCKS-проход через ограничитель в процессе панели. Внутри этого прохода UDP передаётся по TCP с сохранением границ датаграмм, чтобы дополнительный заголовок SOCKS не обрезал пакеты на границе буфера ядра. Порты 15879 и 15880 используются на 127.0.0.1 и защищены случайным паролем процесса. Конфликт порта отклоняет применение конфигурации; при ошибке запуска ядра восстанавливается прежний план. Когда ограничений нет, дополнительный слушатель не запускается.

В API клиент принимает объект `speedLimit`:

```json
{ "enabled": true, "uploadMbps": 5, "downloadMbps": 20 }
```

`enabled: false` отключает ограничение, сохраняя значения для следующего включения. Отсутствие объекта в старом запросе сохраняет существующий лимит. Объект входит в экспорт/импорт клиентов, настройки входящих и синхронизацию нод.

Проверки: `go test -race ./internal/clientlimit`; серверные тесты `TestClientSpeedLimit*`. Для проверки с настоящим ядром задайте `HIDDIFY_CONFIG_CHECK_BINARY=/absolute/path/hiddify-core` и запустите `go test ./internal/web/service -run TestClientSpeedLimit -v`.

## Mieru, Sudoku и MASQUE

Эти протоколы используют тот же бюджет скорости клиента, что и остальные:
параллельные VLESS, Mieru, Sudoku и MASQUE не получают отдельные полные лимиты.
Mieru учитывается после расшифровки потока, Sudoku — после авторизованного
handshake по хешу клиентского ключа, MASQUE — по авторизованной CONNECT-IP
сессии на уровне IP-пакетов. Mieru/Sudoku включают служебное framing внутри
расшифрованного потока, MASQUE включает заголовки IP; скорость полезных данных
может быть немного ниже установленной. QUIC/HTTP управление MASQUE не ограничивается.

Нужны совместимые сборки `mita`, `sudoku-tunnel` и ядра из поставки панели.
Исходники и патчи закреплены в `deploy/speed/`; сборка компонентов выполняется
через `python3 tools/build-speed-components.py --output /absolute/output`.
Сборщик ядра `tools/build-hiddify-core.sh` применяет MASQUE-патч автоматически.
Обычные upstream-бинарники не умеют запрашивать общий бюджет: панель проверяет
совместимость и отклоняет применение лимита, если компонент её не поддерживает.
Обновляйте панель вместе с компонентами. Обновление Sudoku на несовместимый
upstream при включённых лимитах отклоняется с восстановлением предыдущего бинарника.

Разрешения на байты передаются по защищённому случайным паролем loopback-соединению
на существующем порту ограничителя. Трафик пользователя через этот управляющий
канал не передаётся. Данные подключения хранятся в приватном служебном файле с правами 0600;
в окружение процессов передаётся только путь к нему. Изменение плана закрывает
выданные подключения, отменяет ожидания и перезапускает управляемые Mieru/Sudoku
при ближайшем согласовании состояния. При недоступности ограничителя активные
ограничиваемые соединения завершаются, обхода лимита через прямой выход нет.

Применение нового лимита Mieru/Sudoku сначала останавливает затронутый процесс,
затем публикует общий план и запускает процесс заново через согласование состояния.
Ключи Sudoku сохраняются. При таком обновлении остальные клиенты того же процесса
тоже могут переподключиться. Если для включённого лимита ещё нет применённого
бюджета, соответствующий sidecar не запускается без ограничения.

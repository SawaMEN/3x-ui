# Общий HTTPS-вход на TCP 443

В настройках Telemt WEB выберите **Nginx / Caddy / HAProxy → Общий HTTPS-вход на порту 443**. Режим доступен и в отдельной настройке Telemt WEB, и во входящем MTProto с включённым WEB Proxy.

| Сервис | Пример публичного адреса | Внутренний адрес |
|---|---|---|
| Панель | `https://web.example.com/admin-path/` | `https://127.0.0.1:8443/admin-path/` |
| Подписка | `https://web.example.com/sub-path/<id>` | `http://127.0.0.1:2096/sub-path/<id>` |
| Telegram WEB | `web.example.com:443`, путь `telegram/web` | Локальный порт, выделенный Telemt |
| Заглушка | `https://web.example.com/` | Тот же локальный Telemt |
| Дополнительное TLS-подключение | `vpn.example.com:443` | TLS на `127.0.0.1:9443` |
| VLESS REALITY (альтернатива TLS) | `web.example.com:443`, отдельный SNI | REALITY на `127.0.0.1:9443` |

- У панели должен быть TLS-сертификат и отдельный путь входа. TCP 443 нужно освободить для выбранного входа. Панель подключается к существующим внутренним портам через loopback. Если слушатели сейчас привязаны ко всем адресам, их привязка сохраняется.
- Если публичный URL подписок пуст, панель использует домен Telemt WEB. Для пустого пути Telemt WEB используется `telegram/web`. Проверка перед включением покажет пересечения путей.
- Дополнительные подключения необязательны. Можно одновременно выбрать до 64 локальных входящих подключений: NaiveProxy HTTPS, VetrOFF Proxy (HTTP/2, WSS, XHTTP), AnyTLS, TrustTunnel, MASQUE (HTTP/1–2), ShadowTLS (один фиксированный SNI) или совместимый VLESS, VMess, Trojan либо Shadowsocks с TLS/REALITY. Для TLS требуется отдельное имя SNI с сертификатом и DNS на сервер; для REALITY — один отдельный SNI, а публичным адресом станет домен Telemt WEB. Существующий одиночный выбор автоматически переносится в список. Каждое подключение должно иметь уникальный SNI. При совпадении SNI маршруты не активируются.
- Подключения на loopback или wildcard-адресе с портом, отличным от 443, можно выбрать сразу: публичный TCP 443 направляется на существующий локальный порт. Старый слушатель не изменяется и остаётся доступен согласно текущему firewall. Подключения, уже занимающие TCP 443, появляются в списке при совместимости и требуют подтверждённого переноса. Панель добавит публичный адрес с портом 443 в подписки и обновит маршрут при изменении внутреннего порта или SNI. Протоколы без TLS/SNI и UDP-подключения в этот режим не входят. Публичный TCP 443 должен принадлежать общему входу, а не дополнительному подключению.

- MASQUE с HTTP/3 и VetrOFF Proxy с транспортом HTTP/3 не маршрутизируются через общий TCP 443: для него необходим отдельный UDP-вход. Если задан Public HTTPS origin, он должен совпадать с выбранным SNI и публичным портом 443. Для Bond hub/discovery укажите этот origin явно.
- FPTN, Snell, Mieru, Sudoku и другие протоколы без проверенного совместимого TLS/SNI-входа пока не публикуются через этот режим. UDP и ICMP остаются отдельными.

## Различия фронтендов

Nginx и Caddy самостоятельно обслуживают HTTPS, панель, подписки и Telemt. Если выбраны VPN-подключения, отдельная служба `3x-ui-telemt-ingress.service` принимает TCP 443 и направляет TLS по SNI без расшифровки. WEB-запросы передаются выбранному HTTPS-серверу по закрытому Unix-сокету с PROXY protocol. Для Caddy требуется модуль proxy_protocol (обычно Caddy 2.7+). HAProxy использует одну службу без дополнительного диспетчера. При переключении между режимами выбор подключений сохраняется.

MASQUE: выберите только HTTP/1 и/или HTTP/2, иначе подписка может предпочесть недоступный HTTP/3. ShadowTLS: допускается отдельный входящий ShadowTLS без wildcard и дополнительных SNI; клиент получает публичный адрес Telemt и исходное имя TLS-рукопожатия. ShadowTLS как дополнительная обёртка другого протокола пока не поддерживается.
FPTN имеет независимый выбор SNI в клиенте, включая spoofing, а существующий токен не фиксирует это имя; одного hostname сертификата недостаточно для безопасного маршрута. Snell, Mieru, Sudoku и OpenFlux direct не гарантируют совместимый TLS ClientHello с уникальным SNI. Не публикуем для них ложный адрес TCP 443.

Проверка готовности включает фактический процесс и владельца TCP 443. При изменении только VPN-маршрутов отдельный TCP-диспетчер перезагружается без перезапуска HTTP-фронтенда. Переключение ожидает освобождения порта старым процессом; сторонние HTTPS-сайты Nginx не отключаются автоматически. Нативная интеграционная проверка CI запускает реальные Nginx, Caddy и HAProxy, включая совместный режим.

## Нативные TCP-диспетчеры

При применении настроек панель автоматически выбирает Nginx stream с ssl_preread, если модуль уже установлен, или Caddy Layer 4, если сборка содержит TLS matcher, proxy handler и PROXY protocol listener. В остальных случаях остаётся HAProxy. Старые сохранённые конфигурации продолжают использовать HAProxy до повторного применения. Выбранный движок хранится в состоянии и не меняется при фоновом обновлении маршрутов. Для Nginx используется отдельная stream-конфигурация, без изменения системного nginx.conf. В Nginx stream PROXY-заголовок снимается на закрытом внутреннем сокете перед передачей VPN-протоколу; Caddy отправляет его только веб-фронтенду. UDP 443 остаётся независимым от TCP 443.

### Автоматический выбор и диагностика

Кнопка «Выбрать совместимые автоматически» выбирает до 64 подходящих включённых loopback TCP-подключений с уникальными SNI, исключая домены WEB и повторяющиеся имена. Выбор можно изменить до применения. Сохранённые входящие подключения не переносятся на другие порты и не публикуются без явного применения. Preflight показывает TCP-движок и фактического владельца UDP 443, включая сохранённые резервы VetrOFF HTTP/3. UDP остаётся прямым подключением: одновременно занять один и тот же UDP-адрес/порт несколькими независимыми QUIC-серверами нельзя. Caddy WEB использует только HTTP/1 и HTTP/2 и не захватывает UDP 443.

### Мастер предварительной настройки

В обеих формах WEB Proxy предварительная проверка теперь показывает план внутренних и публичных адресов, нужные WEB-алиасы, непересекающийся путь, решение по TLS и рекомендации для переноса панели/подписок с 443. «Подставить рекомендации в форму» меняет только черновик; после изменения запускается повторный preflight. Выбор внутреннего порта Telemt использует проверку сохранённых подключений и системных резерваций, а не только открытый сокет. Перенос работающей панели, подписок и VPN на другие порты не выполняется автоматически. Для нескольких доменов нужен действующий общий сертификат; для одного домена доступен прежний автоматический HTTP-01.

### Перенос портов с защитой доступа

Для локальной панели при выключенном WEB Proxy мастер предлагает перенос TCP 443 в диапазон 18080–18179. Операция сохраняет старые и новые порты в одной транзакции SQLite и перезапускает слушатели. После перезапуска откройте новый адрес и подтвердите доступ в течение трёх минут. Без подтверждения или при ошибке запуска прежние порты восстанавливаются; после аварийного завершения процесса незавершённая миграция откатывается при старте. Адреса привязки, пароли, сертификаты и клиентские настройки не меняются. Перед переносом откройте новый порт в firewall, после подтверждения вернитесь к мастеру WEB Proxy. UDP и VPN-подключения не переносятся этой операцией.

### Предварительный план переноса VPN

Мастер перечисляет локальные подключения, резервирующие TCP 443, включая отключённые. Для обычных VLESS, VMess и Trojan с совместимым TCP TLS/REALITY и одним SNI предлагаются отдельные свободные порты в диапазоне 18200–18399 и loopback-привязка. Исключаются смешанные и UDP-транспорты, внешние sidecar-протоколы, явные fallback, обёртки, отдельные IP и конфликтующие SNI. Это только предварительный план: параметры входящих не изменяются, обычная проверка порта 443 по-прежнему блокирует запуск при конфликте. Не переносите действующие входящие вручную без проверенного маршрута и плана возврата.

### Экспериментальный API применения переноса VPN

Standalone WEB API принимает дополнительный массив vpnMigrations с id, newPort и revision из актуального preflight. Операция пока доступна только для обычных TLS VLESS/VMess/Trojan на работающем native core, при выключенном WEB Proxy и отсутствии managed MTProto. Все резервирующие TCP 443 подключения должны быть выбраны; REALITY и sidecar-протоколы остаются только в предварительном плане. Старые listen/port записываются в журнал вместе с изменениями, теги и клиентские данные не переписываются. После перезапуска ядра проверяются локальные TCP-слушатели, выполняется обычный запуск WEB и проверяется публикация маршрутов. При ошибке запуска восстанавливаются исходные порты и ядро; незавершённый журнал восстанавливается при запуске панели. Отключение standalone WEB с активным журналом возвращает исходные VPN-порты. Полноценная проверка клиентской авторизации и доступности извне не заменяется локальной проверкой. Для применения в редакторе managed MTProto пока требуется отдельная интеграция.

Автоматическое применение расширено на TCP NaiveProxy, AnyTLS, MASQUE только HTTP/1–2 и TCP Shadowsocks с TLS. Для занятого TCP 443 проверяется абсолютный путь исполняемого файла каждого процесса через /proc; стороннее ядро или Caddy с совпадающим именем не допускается. REALITY явно помечается как требующий авторизованной проверки, VetrOFF/TrustTunnel и смешанные TCP/UDP-профили пока не переносятся автоматически.

VetrOFF TCP-профили теперь допускаются к переносу с сохранением отдельного HTTP/3. Если HTTP/3 наследует исходный TCP bind, операция закрепляет прежний UDP-адрес в h3Listen и журналирует только прежнее значение этого поля. При возврате восстанавливается исходное значение (или отсутствие поля). До и после переноса проверяется UDP-слушатель и путь исполняемого файла VetrOFF. После изменения запускается штатное согласование externalvpn с учётом отключённых клиентов. Профили с основным H3-транспортом не переводятся в TCP; UDP-ретрансляция не отключается. Проверка сокета не является полноценным HTTP/3 клиентским тестом.

Для VLESS REALITY добавлена экспериментальная авторизованная проверка: существующая ссылка активного клиента без лимита трафика/IP преобразуется в профиль временного native-core процесса. До переноса проверяется исходный вход; после запуска — внутренний порт и общий TCP 443. Запрос HTTPS к generate_204 должен вернуть 204; если исходная проверка не проходит, перенос не начинается, если последующая — выполняется откат. Учётные данные не записываются в журнал. Требуется доступ к тестовому HTTPS-ресурсу; локальный тест не доказывает доступность из внешних сетей. TrustTunnel по-прежнему использует TCP и QUIC на одном bind, ShadowTLS требует отдельной проверки прикладного трафика, поэтому эти режимы не переводятся автоматически.

ShadowTLS v3 с фиксированным SNI и собственным внутренним ключом теперь использует авторизованный probe через цепочку ShadowTLS → Shadowsocks 2022. Перед изменением проверяется старый порт, после запуска — внутренний порт и общий вход. Неудачная проверка отменяет операцию либо запускает откат. Дополнительная обёртка ShadowTLS и wildcard SNI остаются исключёнными. TrustTunnel явно помечается как несовместимый с автоматическим переносом: текущий renderer использует общий listen_address для HTTP/1, HTTP/2 и QUIC; TCP-only маршрутизация не должна молча перемещать UDP.

TrustTunnel: добавлен явный режим HTTP/1–2 (TCP only). По умолчанию существующие подключения сохраняют HTTP/1, HTTP/2 и QUIC. Только после отдельного выбора TCP-режима и сохранения разрешается перенос; до и после него проверяется отсутствие UDP-сокета TrustTunnel. QUIC не отключается самой миграцией. В актуальной официальной документации TrustTunnel (https://github.com/TrustTunnel/TrustTunnel/blob/master/CONFIGURATION.md) нет отдельных listen_address для TCP и QUIC. Для сохранения QUIC при совместном переносе нужен отдельный механизм публикации UDP, который пока не реализован. QUIC-only клиенты не будут работать после ручного перехода на TCP.

#### Подготовка раздельного режима TrustTunnel

Вместо NAT или UDP-прокси подготовлена пара конфигураций: HTTP/1–2 на loopback и QUIC-only на исходном IP:443. Общие credentials.toml, hosts.toml и SOCKS5 egress сохраняют идентичность клиентов и ограничения доступа к частным сетям; метрики используют отдельные локальные адреса. Генератор не записывает файлы, не запускает процессы и не изменяет настройки. Предварительная диагностика показывает исходный QUIC bind. Автоматический перенос dual-transport профиля остаётся заблокирован до реализации общего супервизора, независимых счётчиков, резервирования UDP и проверки обоих процессов/отката. Это подготовка, а не включённая функция. Документация upstream: https://github.com/TrustTunnel/TrustTunnel/blob/master/CONFIGURATION.md.

Менеджер подготовлен к единому split runtime: оба дочерних процесса запускаются и останавливаются вместе; выход одного завершает второй, неудачный запуск QUIC освобождает TCP. Для запуска проверяются оба локальных metrics endpoint. Счётчики TCP и QUIC дифференцируются независимо и суммируются по клиенту; неудачный опрос одного не продвигает baseline другого. Используется общий владелец трафика и существующий атомарный механизм записи. Runtime-поле TrustTunnelQUICBind пока не заполняется из БД: публичный UDP должен быть зарезервирован, а перенос и откат — журналированы перед включением функции. Проверка metrics не заменяет проверку реального QUIC-клиента.

Раздельный TrustTunnel теперь подключён к standalone WEB-миграции: сохраняется служебное поле trustTunnelQuicBind в одной транзакции с listen/port и журналом. Проверки конфликтов учитывают отдельный UDP 443 и сохраняют этот адрес при обычном редактировании. До и после переноса проверяется точный PID управляемого QUIC-слушателя; внутренний TCP-порт не должен иметь UDP-сокет TrustTunnel. При возврате удаляется только служебное поле, исходный комбинированный слушатель восстанавливается. Это проверка локальных сокетов и TLS, не полноценный тест авторизованного QUIC-клиента.

### Черновик управляемого MTProto WEB

Редактор позволяет подготовить отключённый локальный MTProto WEB с sharedIngress и явным migrationDraft=true. Черновик не резервирует TCP 443 и не запускает Telemt; остальные выключенные подключения продолжают резервировать свои порты. Обычное включение черновика отклоняется. Предварительная диагностика исключает редактируемый MTProto из списка мигрируемых VPN. Это первый этап интеграции: отдельное подтверждённое применение, запись владельца и восстановление managed WEB ещё не подключены.

Черновик можно применить отдельным POST /panel/api/telemt/webproxy/managed-migration. Запрос содержит inboundId, draftRevision и vpnMigrations; настройки WEB берутся из сохранённой записи, не из несохранённой формы. Перенос VPN и активация MTProto записываются в одной транзакции с журналом; восстановление сначала выключает владельца MTProto и возвращает его к черновику, затем восстанавливает VPN. При отключении владельца или отсутствии активных клиентов reconcile возвращает исходные порты. Требуются отдельные проверки реального запуска и CI.

### Финальная проверка: исправления и CI

Проверка nginx -T различает TCP и UDP/QUIC, учитывает многострочные и quoted listen; порт UDP 443 больше не блокирует TCP frontend сам по себе. Проверка владельца TCP после перезагрузки входит в область отката. Применение сохранённого MTProto-черновика недоступно при несохранённых изменениях формы. В отдельный CI job добавлены регрессии переноса, журналов, managed WEB и счётчиков; существующий тест официального TrustTunnel endpoint расширен на split режим (проверка UDP-сокета QUIC-only и авторизованный HTTP/2 TCP/UDP payload). Это не проверка полноценной QUIC-сессии; её нужно выполнить отдельно.

Проверка TrustTunnel расширена авторизованным HTTP/3 CONNECT через настоящий официальный endpoint: проверяется сертификат, отклонение неверного пароля, передача echo-payload через тестовый SOCKS и отсутствие лишнего запроса к egress. Сценарий запускается для combined и split, использует уже закреплённую зависимость quic-go. Журнал миграции дополнительно отклоняет повторяющиеся ID и внутренние порты до применения или восстановления. Результат CI требуется подтвердить отдельно.

#### Реальная проверка CI и ограничение upstream TrustTunnel

CI для da6495d: Go release builds amd64/arm64, frontend build, web/service и web/controller прошли; OpenFlux frontend typecheck обнаружил TS2339 в Hysteria, sidecar-egress обнаружил отказ split QUIC startup. У официального TrustTunnel v1.1.0 и v1.3.1 функция listen_tcp в lib/src/core.rs открывает TCP даже при отсутствии HTTP/1 и HTTP/2 (accept just for pings). Поэтому одного исключения TCP-таблиц недостаточно. Теперь до переноса выполняется изолированный локальный capability probe: занятый TCP-порт, отдельный QUIC endpoint на том же номере UDP, тестовые credentials/cert и локальные метрики. При несовместимости перенос блокируется без изменения действующих подключений. Официальный комбинированный HTTP/3 тест остаётся обязательным; split интеграция выполняется только с прошедшим probe бинарником, а TRUSTTUNNEL_REQUIRE_SPLIT=1 делает её обязательной для совместимой сборки. Для полной поддержки требуется upstream исправление или собственная проверенная сборка TrustTunnel. Hysteria URI теперь сужает discriminated union по network перед чтением hysteriaSettings.

### Собственный компонент TrustTunnel 1.3.1-xui.1

Исходник закреплён на 113cdc89559b9d2698e1477b3d0af89e95c0b7cf (v1.3.1). Патч в tools/trusttunnel/build.sh не открывает TCP, если отключены HTTP/1 и HTTP/2; combined/TCP-only не изменены. Отдельный workflow собирает Linux x86_64/aarch64 в Ubuntu 22.04 (glibc >= 2.35), требует успешных авторизованных HTTP/2 и HTTP/3 тестов в combined и split. Публикация отдельного тега trusttunnel-v1.3.1-xui.1 выполняется вручную только после обеих проверок, не меняет latest релиз панели. Установщик предпочитает проверенный компонент после публикации, сверяет точный asset URL, SHA-256, версию и локальную возможность QUIC-only до замены. До публикации остаётся официальный источник, более новая официальная базовая версия имеет приоритет; при наличии split конфигурации несовместимая версия не заменит рабочий бинарник. Сборка, тесты и публикация пока должны быть подтверждены в Actions. Для систем с glibc ниже 2.35 потребуется отдельная musl сборка.

#### Повторная сборка компонента после CI

Обе архитектуры 1.3.1-xui.1 успешно скомпилировались, combined HTTP/2 и авторизованный HTTP/3 прошли. Split capability probe завершился timeout. В upstream Http1Codec::new безусловно извлекает listen_protocols.http1 через unwrap; тот же кодек использует локальный metrics endpoint, в том числе при отключённом публичном HTTP/1. Патч дополнительно использует исходный default_upload_buffer_size при отсутствии HTTP/1, не включая публичный TCP. Диагностика тайм-аута теперь содержит последнюю причину проверки и ограниченный лог тестового процесса. Исправлены семь замечаний golangci из CI. При push в main публикация отдельного компонента теперь автоматически выполняется только после двух успешных обязательных job и проверки обеих SHA-256 сумм; уже опубликованные архивы не заменяются. Повторная сборка и split тесты ещё требуют подтверждения.

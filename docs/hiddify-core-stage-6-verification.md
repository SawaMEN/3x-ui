## Источник и сохранение статистики

Подтверждённый контракт — метод
`/v2ray.core.app.stats.command.StatsService/QueryStats`. В исходниках владельца
`experimental/v2rayapi/stats.go` TCP, UDP и flow trackers начисляют байты по
`metadata.Inbound` и `metadata.User`. Ответ содержит
`inbound>>>tag>>>traffic>>>uplink/downlink` и
`user>>>email>>>traffic>>>uplink/downlink`. Outbound counters не складываются
с пользовательскими: это исключает двойное начисление одного потока.

Панель теперь всегда опрашивает Hiddify с `Reset=false`. Потерянный ответ RPC
не обнуляет счётчики. Таблица `core_traffic_checkpoints` хранит последнее
полученное значение каждого счётчика и идентификатор процесса ядра. Дельта,
пользовательский/inbound трафик и контрольная точка сохраняются одной
транзакцией через существующий serial traffic writer. Ошибка записи откатывает
весь снимок. Следующий опрос повторно вычисляет дельту из накопительных данных.

Контрольная точка переживает перезапуск панели и перенос/экспорт БД. Таблица
включена в `allModels` и `migrationModels`; SQLite copy test проверяет именно
сохранение её значений. PostgreSQL использует тот же GORM upsert, с пакетами
по 200 строк; отдельный PostgreSQL server в этой среде не использовался.

Рабочая эпоха — PID и системное время создания процесса. Она сохраняется при
adoption после перезапуска панели и меняется при контролируемом restart ядра,
включая повторное использование PID. Эпоха проверяется до и после RPC: снимок,
пересекающий смену процесса, отклоняется. Для изолированных процессов, которые
не допускают adoption, используется PID и сохранённое время запуска.
Неудача определения рабочей эпохи возвращает ошибку и не начисляет снимок.

При новой эпохе накопленные итоги БД сохраняются, а новые счётчики начисляются
от нуля. Старые контрольные точки убираются; история по каждой эпохе не растёт.
Ручной сброс трафика в панели не очищает контрольные точки и не начисляет
старые байты заново. Контрольная точка также закрепляет ID записи трафика:
после email edit опрошенные источники продолжают начисляться прежнему
владельцу, даже если его старое имя занял другой пользователь. Нулевые значения сохраняются, поэтому наблюдаемый сброс
счётчика в той же эпохе также учитывается. Отрицательные и повторяющиеся
пользовательские/inbound counters отклоняются до записи. Разделитель `>>>`
в пользовательском имени не ломает разбор имени счётчика.

## Лимиты и жизненный цикл

После фиксации трафика выполняется общий lifecycle: отложенный старт срока,
автопродление, истечение срока, клиентские и inbound квоты. Maintenance
выполняется и при пустом снимке. Её ошибка не откатывает уже сохранённый трафик
и не заставляет повторно начислять дельту; следующий опрос повторяет maintenance.
Локальные изменения применяются после DB commit через batch/apply этапа 5.
Попутно исправлен short-circuit, который мог пропустить local apply при уже
выставленном `needRestart`.

После сохранения запрета активные пользовательские сессии и сессии отключённых
локальных inbounds закрываются через Clash API. Сетевые вызовы выполняются
вне serial writer. Частичный отказ закрытия сохраняет ошибку; poll пишет warning
и повторяет отключение в следующем цикле. Эта ошибка не блокирует применение
нового конфига и не превращает успешную запись трафика в повторное начисление.

## Онлайн, IP и сессии

`internal/hiddify/sessions.go` — общий адаптер service и local runtime.
Local SessionRuntime больше не вызывает sing-box connection API на 10091
для Hiddify. Выбор ядра читается один раз на операцию. Authenticated user,
inbound, TCP/UDP, ID, адреса и байты берутся из Clash `/connections`.
Профиль сборки уже включает overlay `metadata.user`.

IPv4-mapped IPv6 и развёрнутый IPv6 приводятся к единому представлению.
Пустой user не выбирает анонимные сессии при пользовательском отключении;
пустой inbound не превращается в отключение всех соединений. Сессии без ID
пропускаются, отсутствующее время начала не превращается в отрицательную дату.
При ошибке получения присутствия фоновый job очищает старый local online
snapshot. Историческое `last_online` в БД сохраняется.

## Открытая приёмка и границы гарантий

Настоящий loopback runtime тест повторно запущен с
`HIDDIFY_RUNTIME_BINARY`. Он останавливается до обслуживания соединений:
`start service: create netlink socket: operation not permitted`.
Для полной приёмки нужны TCP/UDP/flow-трафик, квоты, онлайн и отключение
на сервере, где разрешён старт собственного ядра.

Подтверждена защита от потери ответа RPC, DB failure и повторного начисления
после рестарта панели. Строгая гарантия сохранения **каждого** байта при смерти
ядра не заявляется: текущий форк хранит счётчики в памяти. При SIGKILL/сбое
питания теряются ещё не опрошенные байты. Контролируемая остановка делает
предварительный poll, но между ним и Stop остаётся окно для нового трафика.
Для закрытия этой границы потребуется durable/final counter journal в ядре
с отдельной приёмкой; одна контрольная точка панели его не заменяет.
Внешний SIGHUP/reload в том же PID и сторонние destructive QueryStats не
входят в поддержанный lifecycle: используйте restart/apply панели.

Поэтому реализация этапа 6 добавлена, но полная приёмка «нет потерь байтов
при остановке ядра» остаётся открытой. Смена default core и автоматическая
миграция/удаление старых ядер относятся к следующим этапам.

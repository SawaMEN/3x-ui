# Zapret2 — выборочный виртуальный outbound в 3x-ui

> Экспериментальная интеграция в PR #368. Не использовать на рабочем VDS до завершения CI и Linux-проверок.

## Схема

Телефон (VLESS/NaiveProxy) → российский VDS с 3x-ui → выбранный virtual outbound `zapret2` → локальный SOCKS → помеченный прямой выход → `nftables`/`nfqws2` → интернет с IP этого VDS.

Другие входящие подключения и процессы сервера не получают метку zapret2 и продолжают пользоваться обычными маршрутами. Zapret2 не является самостоятельным VPN-протоколом и не влияет на зашифрованный участок от телефона до VDS.

## Установка

1. Требуются Linux amd64/arm64, `nftables` c NFQUEUE и права `CAP_NET_ADMIN` (текущая реализация требует UID 0).
2. Откройте «Настройки → Установка и обновление компонентов» и установите **Zapret2**.
3. Панель получает архив только из [официальных релизов bol-van/zapret2](https://github.com/bol-van/zapret2/releases), проверяет SHA-256 из GitHub Release API и распаковывает его в отдельный каталог. Системный `install_easy.sh` не запускается.
4. После установки появляется вариант **zapret2** среди исходящих подключений.

## Создание маршрута

1. Создайте исходящий `zapret2` с уникальным тегом, например `zapret-rf`. Укажите свободный локальный порт (например, 15900), профиль обработки TCP и, при необходимости, UDP/QUIC.
2. Для выбранного inbound VLESS или NaiveProxy настройте правило маршрутизации с `outboundTag = zapret-rf`.
3. Остальные inbounds оставьте на `direct` либо на существующих outbound. Мост работает только на `127.0.0.1`; открывать локальный порт в публичном firewall не нужно.

## Автоматическая диагностика

В форме подключения укажите несколько реальных тестовых доменов и нажмите «Автоматически проверить и подобрать стратегию». Доступны три режима сканирования: **быстрый**, **полный** и **максимальный**. Можно выбирать число повторов (1–3), проверять IPv6, а при включённом UDP — QUIC.

1. Панель временно останавливает **только свои** NFQUEUE-очереди zapret2 на время эксперимента и пытается вернуть прежнюю конфигурацию после проверки. Другая маршрутизация VPS не затрагивается.
2. Официальный `blockcheck2.sh` запускается пакетно и возвращает успешные сочетания с покрытием `COVERAGE`: доля сайтов, доступных с данной стратегией.
3. Победители выбираются **независимо для HTTP, HTTPS, QUIC и IP-семейства**, при этом из покрытия исключаются сайты, доступные без обхода, а к автоматическому применению допускаются только стратегии с подтверждённым успехом минимум на двух третях целей, которым обход действительно требовался.
4. Каждая последовательность опций проверяется на допустимые параметры и затем проверяется через `nfqws2 --dry-run` текущего официального бинарника. Опции с внешними файлами, командами или неподдерживаемыми параметрами исключаются из автоприменения.
5. Сохраняются **точные аргументы**, дата сканирования, домены, результаты и режим проверки. Нажмите «Сохранить» у виртуального outbound, чтобы применить их. Каждое другое подключение остаётся без изменений.
6. Для непроверенных сочетаний протокола/IP остаётся базовый профиль. При отсутствии надёжного результата настройки не изменяются, а в интерфейсе отображается отчёт с предупреждением.

**Важно:** до первого запуска диагностики профиль `auto` использует исходный сбалансированный шаблон. Подбор запускается пользователем, а не по фоновому расписанию: массовые пробы могут временно повлиять на Anti-DPI обработку действующих соединений и вызвать ограничения со стороны целевых сайтов. Повторная проверка полезна после смены VDS/провайдера или при ухудшении доступности. Сканирование на российском VDS не гарантирует обход DPI на участке «телефон → российский сервер».

## Безопасность и отключение

- Весь системный трафик не перенаправляется: собственная таблица `inet xui_zapret2` ставит в NFQUEUE только выходящие пакеты, помеченные выделенным outbound.
- В правилах есть `queue bypass`: при падении обработчика пакеты могут уйти напрямую без Anti-DPI. При сбое применения настроек выполняется попытка восстановления прежних очередей. Метки внутренних генерируемых пакетов `nfqws2` исключены из очередей во избежание петли.
- Для удаления переключите маршруты с `zapret-rf`, удалите virtual outbound, примените настройки, затем удалите компонент. Активный процесс или существующий outbound препятствуют удалению.
- Для диагностики используйте `nft list table inet xui_zapret2`, проверку процесса `nfqws2` и прослушивания выбранного порта на `127.0.0.1`.

## Что ещё необходимо проверить

Реальные TCP/UDP-соединения на Linux, доступность IPv4/IPv6, запуск и остановку при рестарте Xray/sing-box, конфликт портов, откат правил, автообновление официального архива и пользовательские сценарии с NaiveProxy.

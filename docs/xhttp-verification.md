# Проверка XHTTP — 2026-10-12

Проверена реализация панели на базе main `e386064`. В текущем проекте серверное ядро — Hiddify Core; клиентские Xray-конфигурации и ссылки требуют отдельной проверки.

## Исправленные проблемы

- Ссылки из веб-панели теряли `scMinPostsIntervalMs`, `uplinkChunkSize`, `noGRPCHeader`, XMUX и `downloadSettings`, хотя серверные подписки могли их передавать.
- Схема формы удаляла `downloadSettings` при загрузке и сохранении inbound.
- Нормализация inbound удаляла `uplinkChunkSize`, нужный клиентской подписке.
- Формы не раскрывали `extra` с приоритетом Xray: при наличии `extra` вне него действуют только `host`, `path`, `mode`. Изменения формы могли игнорироваться ядром, XMUX внутри `extra` не попадал в редактор.
- Генераторы ссылок, JSON и Mihomo-подписок не учитывали вложенный `extra` последовательно.
- JSON-подписки удаляли числовые ограничения upload из API-конфигураций из-за проверки только строкового типа. Ссылки и Mihomo также пропускали числовые диапазоны.
- JSON-подписки включали глобальный обычный Mux для XHTTP без явного XMUX. Теперь обычный Mux не добавляется ко всем XHTTP-профилям.
- Hiddify-транслятор отклонял inbound с клиентским `downloadSettings`, сохранённым для подписок. Эти данные сохраняются в исходной конфигурации, но не настраивают серверный listener.
- Старые конфигурации с `Host` внутри `headers` отклонялись обоими ядрами. Теперь заголовок переносится в поле `host`; явный `host` имеет приоритет, прочие заголовки сохраняются.

## Проверки

- 237 тестов frontend: генерация ссылок, импорт, формы inbound/outbound, нормализация streamSettings, session ID.
- TypeScript typecheck.
- Go-тесты `internal/hiddify`, `internal/sub`, `internal/util/link`.
- Проверка сгенерированных Hiddify-конфигураций реальным закреплённым бинарным ядром `sawamen-b5749002266b-panel8` через команду `check`.
- 18 реальных сетевых сценариев VLESS/XHTTP на Xray 26.9.9, собранном из зависимости проекта `52a412d9e2f5`: `auto`/`packet-up` без TLS, все четыре режима с TLS и REALITY, плюс отдельный download для режимов, где он допустим.
- В каждом сетевом сценарии три последовательных запроса передают 458752 байта в обоих направлениях; upload ограничен пакетами 32768 байт. Проверяется полное совпадение данных. Download использует отдельную конфигурацию соединения к тому же локальному listener.

Сетевой тест запускается так:

```sh
XRAY_RUNTIME_BINARY=/path/to/xray go test ./internal/hiddify -run TestXHTTPRuntimeTransfer -v -count=1
```

Для настоящей передачи через Hiddify используйте `HIDDIFY_RUNTIME_BINARY` вместо `XRAY_RUNTIME_BINARY`. Для проверки его конфигураций:

```sh
HIDDIFY_CONFIG_CHECK_BINARY=/path/to/hiddify-core go test ./internal/hiddify -count=1
```

## Границы результата

Реальный запуск Hiddify в данной среде остановился до открытия listener: `create netlink socket: operation not permitted`. Его конфигурации проверены бинарным ядром, но передачу данных через него подтвердить здесь нельзя. Xray-транспорт проверен реальной передачей.

VDS, клиент пользователя, CDN, внешний reverse proxy и HTTP/3 через UDP не проверялись. Проверка локальной передачи не подтверждает доступность порта, сертификатов, CDN-правил или работу в конкретной сети.

Текущий Hiddify-транслятор продолжает явно отклонять неподдерживаемые этим ядром ненулевые `sessionIDTable`, `sessionIDLength` и `serverMaxHeaderBytes`; их поддержка требует отдельного изменения ядра. В этой правке такие параметры не удаляются молча.

Источники: [описание XHTTP разработчиками Xray](https://github.com/XTLS/Xray-core/discussions/4113), структуры и Build-функции закреплённого Xray, схема XHTTP закреплённого Hiddify Core.
